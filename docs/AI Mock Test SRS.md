# 1. Project Overview

**MockTest** is a lightweight web application for students who already
use ChatGPT, Gemini, Claude, local models, or other LLMs to generate
practice questions. The application does not generate questions itself.
Instead, it accepts a standardized JSON mock test, validates it, turns
it into a real exam interface, calculates results, and stores each
user’s test and attempt history.

**Core product idea:** Any LLM → MockTest JSON → Timed Exam → Result →
History.

## 1.1 Problem Statement

Students often ask an LLM to create a mock midterm or final exam, but
the raw chat output is not an ideal exam experience. It may expose
answers too early, provide no timer or question navigation, and does not
provide organized attempt history. MockTest separates content generation
from exam delivery.

## 1.2 Proposed Solution

- Provide a standard JSON format that can be generated by any LLM.

- Allow users to paste or upload the JSON into MockTest.

- Validate the JSON before an exam starts.

- Run a distraction-free, timed multiple-choice exam.

- Automatically calculate the score and show explanations after
  submission.

- Store imported tests and completed attempts for authenticated users.

- Use only Google or GitHub OAuth; no password-based accounts are
  required.

## 1.3 Product Principles

| **Principle**     | **Meaning**                                                                                                          |
|-------------------|----------------------------------------------------------------------------------------------------------------------|
| Lightweight       | Keep dependencies, database structure, and runtime complexity small.                                                 |
| LLM-independent   | No dependency on a specific AI provider and no paid LLM API is required.                                             |
| Fast to use       | A user should be able to import a valid test and start the exam in a few actions.                                    |
| Privacy-conscious | Only the generated mock-test JSON is required; source lecture files do not need to be uploaded to this application.  |
| Simple data model | Store each test and attempt primarily as JSON instead of normalizing every question and answer into separate tables. |

# 2. Scope

## 2.1 In Scope — MVP

- Google OAuth login.

- GitHub OAuth login.

- Authenticated dashboard.

- Paste JSON and upload .json files.

- MockTest JSON Spec v1 validation.

- Save valid tests to the user account.

- Multiple-choice exams with exactly four options per question.

- Exam timer, next/previous navigation, and question navigator.

- Manual submission and automatic submission when time expires.

- Score calculation and answer review.

- Attempt history and test retakes.
- Copy or download incorrect and unanswered questions as JSON for review with an external LLM.

- Delete a saved test and its associated attempts with confirmation.

- Copy-ready prompt that helps users ask an LLM to generate compatible
  JSON.

- Responsive desktop and mobile layouts.

## 2.2 Out of Scope — MVP

- Built-in ChatGPT, Gemini, Claude, or other LLM API integration.

- Username/password authentication, registration forms, password reset,
  or email OTP.

- PDF/PowerPoint lecture extraction inside MockTest.

- Teacher/classroom management, live proctoring, grading by instructors,
  or LMS functionality.

- Short-answer automatic grading.

- Leaderboards, social feeds, chat, notifications, or gamification.

- Redis, microservices, message queues, or a managed external database
  service for the initial MVP. Local PostgreSQL runs through Docker Compose.

# 4. System Architecture

The system follows a small client/server architecture. React + Vite
provides the browser UI, while ElysiaJS runs the application API on Bun.
Clerk handles user authentication and sessions. Drizzle ORM accesses a
PostgreSQL database running in Docker for local development.

# 6. MockTest JSON Spec v1

The mock test format is the interoperability contract between an
external LLM and MockTest. The MVP supports multiple-choice questions
only.

## 6.1 Example

{

"version": "1.0",

"title": "Database Midterm",

"description": "Practice for Chapters 1-5",

"duration_minutes": 60,

"questions": \[

{

"id": "q1",

"type": "multiple_choice",

"question": "What is a primary key?",

"options": \[

"A unique identifier for a row",

"A table name",

"A database server",

"A SQL keyword"

\],

"answer": 0,

"explanation": "A primary key uniquely identifies each row."

}

\]

}

## 6.2 Validation Rules

| **Field**                 | **Required** | **Rule**                    | **Notes**                                |
|---------------------------|--------------|-----------------------------|------------------------------------------|
| version                   | Yes          | Exactly "1.0"               | Used for future compatibility.           |
| title                     | Yes          | Non-empty string            | Recommended max 120 characters.          |
| description               | No           | String                      | Short test description.                  |
| duration_minutes          | Yes          | Integer 1–180               | Countdown duration.                      |
| questions                 | Yes          | Array with 1–100 items      | MVP limit.                               |
| questions\[\].id          | Yes          | Unique non-empty string     | Unique within the test.                  |
| questions\[\].type        | Yes          | Exactly "multiple_choice"   | Only supported MVP type.                 |
| questions\[\].question    | Yes          | Non-empty string            | Question prompt.                         |
| questions\[\].options     | Yes          | Exactly 4 non-empty strings | Displayed in given order.                |
| questions\[\].answer      | Yes          | Integer 0–3                 | Zero-based index into options.           |
| questions\[\].explanation | No           | String                      | Shown after submission, not during exam. |

## 6.3 Error Handling

Validation errors should identify the failing location and expected
correction. Example messages:

- Question 7: options must contain exactly 4 items.

- Question 12: answer must be an integer from 0 to 3.

- questions\[5\].id: duplicate question ID "q6".

- duration_minutes: expected a value from 1 to 180.

# 7. Data Requirements

To keep the MVP small, the application stores each test and attempt as
JSON-oriented records instead of creating separate question and answer
tables.

## 7.1 Application Tables

| **Table**                                 | **Key Fields**                                                                                              | **Purpose**                                                                          |
|-------------------------------------------|-------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------|
| identity reference (no local auth tables) | clerk_user_id stored on app-owned records                                                                   | Clerk owns identity/session data; the app stores the Clerk user ID as the owner key. |
| mock_tests                                | id, clerk_user_id, title, description, duration_minutes, question_count, test_json, created_at, updated_at  | Stores one imported test and its complete JSON payload.                              |
| attempts                                  | id, clerk_user_id, mock_test_id, answers_json, score, total_questions, percentage, started_at, completed_at | Stores one exam attempt and its submitted answers.                                   |

## 7.2 Data Ownership Rules

- Each mock_tests record belongs to exactly one authenticated user.

- Each attempt belongs to exactly one user and one saved mock test.

- All read, update, and delete operations must filter by the
  authenticated Clerk user ID.

- Deleting a saved mock test should also delete its attempts or reject
  deletion unless related attempts are explicitly handled.

# 8. API Requirements

Exact route naming may change during implementation. The following
describes the minimum API surface.

| **Method** | **Route**                | **Auth** | **Purpose**                                 |
|------------|--------------------------|----------|---------------------------------------------|
| GET        | /api/tests               | Required | List the current user’s saved tests.        |
| POST       | /api/tests               | Required | Validate and create a test.                 |
| GET        | /api/tests/:id           | Required | Read one owned test.                        |
| DELETE     | /api/tests/:id           | Required | Delete one owned test and related attempts. |
| POST       | /api/tests/:id/attempts  | Required | Start/create a new attempt.                 |
| POST       | /api/attempts/:id/submit | Required | Submit answers and finalize score.          |
| GET        | /api/attempts/:id        | Required | Read one owned attempt/result.              |
| GET        | /api/history             | Required | List the current user’s completed attempts. |

## 8.1 Server-Side Scoring Rule

The authoritative score should be calculated by the server from the
stored test JSON and submitted answer indexes. The client may calculate
a preview, but the saved result must use server-side calculation so the
user cannot directly submit an arbitrary score.

# 9. User Experience Requirements

## 9.1 Main User Flow

1.  Open MockTest.

2.  Sign in with Google or GitHub.

3.  Open “Create / Import Test”.

4.  Paste JSON or upload a .json file.

5.  Fix any validation errors, then save the test.

6.  Start the test from the dashboard.

7.  Answer questions while the timer runs.

8.  Submit the exam or allow auto-submit at time expiry.

9.  Review score and explanations.

10. Return later to view history or retake the test.

## 9.2 Key Screens

- Landing / Login: product summary and Google/GitHub sign-in buttons.

- Dashboard: saved tests, latest score, attempt count, create/import
  action.

- Import Test: JSON editor/paste area, upload control, validation
  report, save button.

- Exam: title, timer, question, four options, navigation,
  answered/unanswered status, submit button.

- Result: score, percentage, review of each question and explanation.

- History: chronological list of attempts with test name, score,
  percentage, and completion date.

# 11. Security and Privacy

- Clerk OAuth only: no local password hashes or local session tables are
  stored.

- Verify Clerk sessions/tokens on protected API routes.

- Use HTTPS in production.

- Apply ownership checks to every test and attempt query.

- Never trust a score sent by the browser; recompute it on the server.

- Limit JSON upload size (recommended starting limit: 1 MB).

- Do not render imported strings through unsafe raw-HTML APIs.

- Do not persist OAuth provider tokens in the application database
  unless explicitly required; never expose server credentials to the
  browser.

- Provide a clear delete action for user-created tests and associated
  attempt data.

# 12. Lightweight Implementation Constraints

The following constraints are intentional. They prevent the MVP from
becoming unnecessarily complex.

| **Use**                 | **Avoid in MVP**                                   |
|-------------------------|----------------------------------------------------|
| Bun                     | Next.js server features unless later justified     |
| React + Vite            | Prisma if minimal footprint remains the priority   |
| ElysiaJS                | Running multiple API services                     |
| Clerk                   | Local password/session authentication              |
| Drizzle ORM             | Separate AI service                                |
| PostgreSQL              | Microservices                                      |
| Zod                     | Complex global state manager unless needed         |
| JSON-based test storage | Question-per-row normalization                     |

# 13. MVP Acceptance Criteria

- A new user can sign in using either Google or GitHub.

- A valid MockTest JSON v1 document can be pasted or uploaded and saved.

- An invalid document is rejected with actionable validation messages.

- A saved test can be started and all questions can be navigated and
  answered.

- The timer counts down and auto-submits when time expires.

- Manual submission calculates the correct score and percentage.

- The result page shows the correct answer and explanation for review.

- A completed attempt remains visible after signing out and signing in
  again.

- A user cannot access another user’s test or attempt by changing an ID
  in the URL/API request.

- The main workflow works on desktop and mobile-sized screens.
